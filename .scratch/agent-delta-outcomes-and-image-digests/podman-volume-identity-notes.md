# Podman image-volume identity probe

The committed [public volume inspection probe](podman-volume-identity-probe.json) used Podman 5.8.7 with isolated VFS storage. Creating an image-driver volume with a mutable image reference succeeded. Public `volume inspect` returned that reference in `Options.image`, but its `StorageID` was a different opaque value. Passing `StorageID` to `podman image inspect` failed, and the public inspect output had no `StorageImageID` field.

A separate live check on the same Podman version created an image-driver volume with `--opt image=<full local image ID>`. Podman accepted the immutable ID and returned it in `Options.image`; `StorageID` remained different. Inspecting that local image ID returned its registry manifest digest. The agent therefore binds image-volume evidence by checking the exact `Options.image` ID in the owning Podman store and comparing the resulting manifest digest with trusted application labels. It never treats `StorageID` as the source image identity.

The live image-volume check validates the volume API path; it does not establish index-to-platform equivalence for workload outcomes. The separate [reconstructed Podman digest probe](reconstructed-podman-digest-probe.json) observed a canonical running container with an index in `.ImageDigest`, while inspecting its immutable image ID returned the platform manifest in `.Digest`; `RepoDigests` included both. Status keeps the runtime-observed digest and only matches a stored outcome on the same exact digest. A platform-only association therefore does not satisfy an observed index digest, and `lastDelta` remains withheld until a runtime-verified association is available.

A second Podman 5.8.7 VFS check created an image-driver volume from Alpine 3.21, then ran `podman volume create --ignore --driver image --opt image=<Alpine 3.22 image ID> --label ...` with the same volume name. Podman left `Options.image`, labels, and `CreatedAt` unchanged; without `--ignore`, it reported that the volume already existed. The application update path therefore stops the Quadlet units, removes the old image-driver volume, and starts the updated Quadlet so Podman creates it from the new pinned image ID and labels. A lifecycle regression verifies removal happens before start, while the provider test verifies the updated unit's pinned ID and same-create provenance labels.

Existing or `--ignore` volumes without trusted same-create provenance labels remain unknown. The agent withholds the application outcome for those volumes rather than resolving a mutable reference and claiming it describes the volume's held contents.
